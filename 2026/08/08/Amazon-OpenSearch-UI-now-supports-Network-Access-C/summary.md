# Amazon OpenSearch UIがネットワークアクセス制御に対応

Amazon OpenSearch UI now supports Network Access Control

**カテゴリ:** What's New  
**公開日:** 2026-08-06  
**元記事:** [AWS What's New](https://aws.amazon.com/about-aws/whats-new/2026/08/opensearch-ui-network-access-control)

---

## 要約

Amazon OpenSearch UIがネットワークアクセス制御機能をサポートするようになり、IAM条件キーを活用して承認されたネットワークのみへのアクセスを制限できるようになりました。この機能により、AWS環境全体で一貫性のあるデータペリメータを確立し、セキュリティ態勢を強化することができます。

---

## このアップデートで何が変わったか

### 新機能の概要

- **Amazon OpenSearch UIがネットワークアクセス制御機能に対応**
  - IAM条件キーを使用したアクセス制限が可能に
  - 承認されたネットワークのみへのアクセスを強制

- **IAM条件キーの活用**
  - `aws:SourceVpce`: VPCエンドポイント経由のアクセス制限
  - `aws:SourceVpc`: 特定のVPC内からのアクセスのみ許可
  - `aws:SourceIp`: 特定のIPアドレスからのアクセスのみ許可

- **複数レベルでのネットワーク制限実装**
  - アイデンティティベースポリシー: 特定のプリンシパル向けの設定
  - VPCエンドポイントポリシー: エンドポイント経由のアクセス制御
  - リソース制御ポリシー（RCP）: 認証前のアクセス制限

- **リソース制御ポリシーによる早期ブロック**
  - 認証プロセスの前段階でオフネットワークユーザーをブロック
  - セキュリティインシデントのリスク低減

- **全リージョン対応**
  - OpenSearch UIが利用可能なすべてのAWSリージョンで利用可能
  - グローバル環境での一貫したセキュリティポリシー実装が可能

## 対象ユーザー

- **エンタープライズ企業**
  - 厳格なネットワークセキュリティ要件を持つ組織
  - データペリメータ戦略を実装したい企業

- **セキュリティ/コンプライアンスチーム**
  - IAMポリシーとネットワークセキュリティを統合管理する必要がある場合
  - 監査・コンプライアンス要件への対応

- **マルチテナント環境の運営者**
  - テナント間のデータ分離が重要な場合
  - VPCごとのアクセス制御が必要な場合

- **DevOps/Infrastructure チーム**
  - 開発・本番環境の分離を厳格に管理する必要がある場合
  - OpenSearch UIのアクセス制御を一元管理したい場合

## 詳細

### セキュリティの3層構造

Amazon OpenSearch Service のセキュリティは、以下の3つのレイヤーで構成されています：

1. **ネットワークレイヤー**
   - リクエストがドメインに到達するかどうかを決定
   - 公開アクセスまたはVPCアクセスのいずれかを選択
   - VPCアクセスの場合、セキュリティグループで制御

2. **ドメインアクセスポリシー**
   - ドメインエンドポイントに到達したリクエストに対する制御
   - リソースベースのアクセスポリシーにより、特定のURIへのアクセスを許可/拒否

3. **きめ細かいアクセス制御（Fine-grained Access Control）**
   - インデックス、ドキュメント、フィールドレベルでのアクセス制御
   - ロールベースのアクセス管理

### IAM条件キーの組み合わせ例

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": "*",
      "Action": "es:*",
      "Resource": "arn:aws:es:*:*:domain/mydomain/*",
      "Condition": {
        "IpAddress": {
          "aws:SourceIp": "10.0.0.0/8"
        },
        "StringEquals": {
          "aws:SourceVpc": "vpc-12345678"
        }
      }
    }
  ]
}
```

### リソース制御ポリシー（RCP）のメリット

- **認証前制御**: IAM認証プロセスの前にネットワークチェックを実施
- **オーバーヘッド削減**: 不正なリクエストが認証までに到達しない
- **ログ削減**: 不正アクセスの試みがセキュリティログを圧迫しない
- **パフォーマンス向上**: 認証サーバーへの負荷軽減

## ユースケース

### ユースケース1: 企業ネットワーク内アクセス限定

**背景**: 金融企業が OpenSearch UIで顧客データを分析

**要件**:
- 企業ネットワーク内からのアクセスのみ許可
- リモートワーカーはVPN経由でアクセス
- インターネット経由のアクセスは全て拒否

**実装**:
- aws:SourceIp で企業オフィスのIPアドレス範囲を指定
- VPN ゲートウェイのIPアドレスを追加
- リソース制御ポリシーで認証前にブロック

---

### ユースケース2: マルチテナントSaaS環境

**背景**: SaaS プロバイダーが複数の顧客に OpenSearch UIを提供

**要件**:
- テナント間のデータ完全分離
- 各テナントが専用のネットワーク環境を持つ
- テナントのVPCからのみアクセス可能

**実装**:
- 各テナント専用のVPCエンドポイントを設定
- aws:SourceVpce で特定のVPCエンドポイント経由のみを許可
- アイデンティティベースポリシーでテナントごとのデータアクセスを制御

---

### ユースケース3: 開発・ステージング・本番環境の分離

**背景**: DevOps チームが複数環境を運用

**要件**:
- 開発環境は開発者のみアクセス可能
- ステージング環境は QA チームと開発者
- 本番環境は限定されたチームのみアクセス可能

**実装**:
- 各環境ごとに異なるVPCを構成
- aws:SourceVpc で環境別のVPCを指定
- 環境ごとに異なるアイデンティティベースポリシーを適用

## メリット・効果

### セキュリティの強化

- ✅ **承認されたネットワークのみアクセス可能** - 不正アクセスの防止
- ✅ **多層防御アーキテクチャ** - ネットワーク、IAM、きめ細かいアクセス制御の組み合わせ
- ✅ **認証前制御** - オフネットワークユーザーを早期にブロック
- ✅ **監査ログの効率化** - 不正アクセス試行のノイズ削減

### 運用の効率化

- ✅ **一貫したセキュリティポリシー** - AWS環境全体でのデータペリメータ実装
- ✅ **柔軟なアクセス制御** - 複数レベルでのポリシー設定が可能
- ✅ **全リージョン対応** - グローバル環境での統一管理
- ✅ **既存ツールとの統合** - IAM条件キーの標準的な使用法

### コンプライアンス対応

- ✅ **データレジデンシー要件対応** - VPC内に限定したアクセス
- ✅ **監査証跡の管理** - アクセスポリシーの明確な定義
- ✅ **業界標準への準拠** - ネットワークセキュリティベストプラクティスの実装
